# Tazakir — خطة التنفيذ البرمجي المتزامن

> **مرجع النطاق:** `UX Blueprint.md` أولًا، ثم البروتوتايب والـArtifact داخل `design`. المنتج النهائي **إنجليزي LTR افتراضيًا وعربي RTL اختياريًا** وفق الـBlueprint. البروتوتايب يعرض الشاشات الإنجليزية فقط حاليًا، ولا يختزل نطاق التطوير العربي. التصميم ليس تطبيقًا تشغيليًا بعد.
>
> **تقدير تخطيطي:** 17 سبرنت، أسبوعان للسبرنت، بافتراض فريق يضم مطور واجهات تطبيق، ومطور واجهات إدارة، ومطوري Backend، ومختبر QA، ودعمًا جزئيًا للتصميم والبنية. يُعاد تقدير المدة بعد السبرنت الأول وفق حجم الفريق الفعلي؛ التقسيم يحدد التبعيات ومعايير التسليم وليس موعدًا مضمونًا.

## 1. قاعدة العمل التي تمنع تفاوت الواجهة والخادم

كل بند عمل هو **مسار منتج رأسي واحد**، وليس مهمة واجهة منفصلة عن مهمة Backend. لا تُعد قصة السبرنت مكتملة إلا إذا أصبحت واجهتها متصلة بواجهة API حقيقية، وقواعد الخادم وقاعدة البيانات جاهزة، واختُبرت حالاتها الأساسية والخاطئة معًا على بيئة مشتركة. استخدام بيانات Mock مسموح أثناء البناء داخل السبرنت فقط؛ لا يُقبل في عرض نهاية السبرنت.

يبدأ كل مسار باتفاق مشترك بين Frontend وBackend وQA على: المدخلات والمخرجات، حالات التحميل والخطأ، الصلاحيات، انتقالات الحالة، وأمثلة البيانات. يُحفظ عقد API بنسخة موحدة قابلة للتحقق آليًا. أي تغيير في العقد يحتاج تحديث الواجهة والخادم واختبار العقد في نفس طلب التغيير أو في تغييرات مترابطة تُدمج معًا.

**إيقاع السبرنت:** اليومان 1–2 للعقد والنموذج واختبارات القبول؛ الأيام 3–7 لبناء الطرفين بالتوازي؛ اليوم 8 للتكامل على بيئة مشتركة؛ اليوم 9 لاختبار المسار الكامل وإصلاح العيوب؛ اليوم 10 للعرض وقبول المنتج والتخطيط التالي. لا يبدأ مسار يعتمد على مسار غير مقبول؛ يُعاد تقدير السبرنت بدل ترحيل «واجهة شكلية» أو API بلا مستخدم.

**معيار الإنجاز الموحد لكل قصة:**

1. شاشة التطبيق/الإدارة وحالاتها الواردة في الـBlueprint تعمل على بيانات حقيقية من API في بيئة الاختبار.
2. قاعدة البيانات والترحيلات والعقود وصلاحيات الخادم مكتملة، مع معالجة الأخطاء والسباقات وإعادة الطلب حيث تلزم.
3. اختبارات وحدة للقواعد المهمة، واختبار عقد بين الطرفين، واختبار End-to-End لمسار نجاح وفشل واحد على الأقل.
4. مراجعة UX لحالات Loading وEmpty وError وDisabled وSuccess، وإمكانية الوصول في الإنجليزية LTR والعربية RTL معًا؛ لا تُؤجَّل العربية إلى سبرنت نهائي.
5. القياسات والسجلات والتتبع التشغيلي موجودة؛ لا توجد أعطال حرجة أو عالية الشدة مفتوحة عند قبول السبرنت.

## 3. تنظيم العمل داخل كل سبرنت

- **Backlog واحد بحسب المسار:** بطاقة واحدة تجمع تصميم الحالة، Frontend التطبيق/الإدارة، عقد API، Backend، البيانات، QA، والتشغيل. يُمنع إغلاق «جزء الواجهة» أو «جزء الخادم» بوصفه قصة منتج مكتملة.
- **عقود قابلة للاختبار:** كل API يحدد الأمثلة وحالات `success/validation/unauthorized/conflict/expired`، وتتحقق CI من عدم كسر المستهلكين عند التعديل. أي تغيير قاعدة أعمال يحدّث الـBlueprint والعقد واختبارات الطرفين في السبرنت نفسه.
- **بيئة تكامل يومية:** نشر تلقائي لنسخة قابلة للتجربة، بيانات اختبار ثابتة قابلة لإعادة الإنشاء، وتقرير يومي لحالة الرحلات الأساسية. لا يُرحّل التكامل إلى آخر المرحلة.
- **مساحة للعيوب:** يُحجز جزء من قدرة السبرنت لإصلاح عيوب التكامل المكتشفة؛ عيب يمنع مسارًا رأسيًا يُصلح قبل بدء مسار يعتمد عليه.
- **مؤشرات متابعة:** عدد المسارات المقبولة طرفًا لطرف، فشل اختبارات العقود وEnd-to-End، زمن بقاء العيوب، تناقضات الطلبات/المدفوعات، ونسبة تغطية شاشات وحالات الـBlueprint. لا يُقاس التقدم بعدد الشاشات المرسومة أو الـEndpoints وحدها.

**قاعدة اللغتين في كل سبرنت:** أي شاشة أو حالة جديدة تُسلَّم بنصيها العربي والإنجليزي، واتجاهها الصحيح، وبياناتها ورسائل الخطأ من الخادم، واختبار قبول باللغتين. تُعرض الأسماء الرسمية للأندية والملاعب والبطولات من حقول محتوى محلية معتمدة، بينما تبقى المعرّفات وأرقام الطلبات وحالات الأعمال مستقلة عن اللغة. عدم وجود لوحة عربية مقابلة في البروتوتايب لا يُسقط هذا الشرط؛ عند اختلاف تخطيط RTL يراجع المصمم الحالة داخل السبرنت قبل قبولها.

## 4. قرارات يجب حسمها قبل السبرنت المعني

| القرار | الموعد الأقصى | إن لم يُحسم |
|---|---|---|
| إطار التطبيق والإدارة والخادم وقاعدة البيانات والاستضافة | نهاية السبرنت 1 | لا تبدأ عقود إنتاجية متشعبة قبل توحيد البنية. |
| مزود الدفع، المحافظ، وطبيعة BNPL، وبيئة الاختبار ومواصفات Webhook | قبل السبرنت 7، وتفصيل BNPL قبل 9 | تستمر واجهات Adapter واختبارات Sandbox، لكن لا يُقبل تكامل إنتاجي أو يُعلن الدفع جاهزًا. |
| سياسة الإلغاء والاسترجاع ورسوم الخدمة والحجز الجماعي | قبل السبرنت 8؛ الحصص الجماعية قبل 12 | لا تُفعّل عمليات رد الأموال أو تُقبل المرحلة دون سياسة معتمدة. |
| قواعد نقاط الولاء والتداخل مع الخصم | قبل السبرنت 14 | لا تُنفذ عمليات استرداد حقيقية. |
| المحتوى القانوني النهائي وبيانات الشركة وحقوق الشعارات | قبل السبرنت 16/الإطلاق | لا يُنشر محتوى قانوني أو أصول غير معتمدة. |

الخطة تحافظ على نطاق الشاشات والميزات باللغتين كما في الـBlueprint. هذه الضوابط تقلل إعادة العمل والفجوات بين Frontend وBackend، لكنها لا تلغي الحاجة إلى الاختبار والمراجعة قبل الإطلاق.
